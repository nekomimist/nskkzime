# オフラインの品質・遅延評価

2026-10-06、固定版zenzのCPUサーバーを、公開データ200例・自作の診断32例・合成負荷で測定した。
左文脈を渡したAJIMEEの生成第一候補は173/200例で正解だった。IMEの対象文字・候補統合規則まで
適用した候補順では145/200例となる。辞書候補の採点は診断28例で第一候補正解を11例から27例へ
改善したが、文脈なしでは10例に下がった。採点の既定オフと生成1秒・採点300msの期限は維持する。

集計値と実行条件は [2026-10-06の記録](evaluations/2026-10-06-summary.json) に保存した。
これはCLIによる部品と候補順の評価であり、実アプリのキー配送・候補表示までの遅延や、日常利用の
正解率を保証するものではない。実入力の検証範囲は [TSFの検証](TSF_VALIDATION.md) を参照。

## 再現手順

Python 3.11以上（標準ライブラリのみ）、標準のzenz入りReleaseビルド、固定モデル、明示的に
指定するSKK辞書を使う。[zenzの準備](ZENZ.md) を済ませ、リポジトリのルートから実行する。

```powershell
.\scripts\build.ps1 -Configuration Release
git clone https://github.com/azooKey/AJIMEE-Bench.git out/reference/AJIMEE-Bench
git -C out/reference/AJIMEE-Bench checkout --detach 401666cd56d1a570c2021798b64b6da4396bfd45
python -B scripts/evaluate.py --dictionary SKK-JISYO.utf8.L --ajimee out/reference/AJIMEE-Bench/JWTD_v2/v1/evaluation_items.json --rounds 3 --stress-rounds 5 --key-rounds 1000 --output out/evaluation-new
```

参照データを取得済みならcloneは不要。出力先には新しいディレクトリー名を使う。
`--dictionary` は手元の読み取り専用辞書を指定する。辞書は配布・自動取得せず、今回の辞書との
一致は記録のSHA-256で確認する。異なる辞書では順位・採点対象数・正解率が変わる。
`--ajimee` を省略すれば自作32例と負荷試験だけを実行できる。
サーバー・モデル・コア補助プログラムは `--server` / `--model` / `--core` で指定できる。
モデルとAJIMEEの固定ハッシュが一致しなければ評価を拒否する。

`report.md` は結果表、`summary.json` は長さ別・順位差・操作回数を含む集計、`metadata.json` は
版・ハッシュ・実行条件を保持する。`requests.jsonl` には**評価用に明示した読み・文脈・正解・候補**を
保存する。`lookups.json` と `core.json` はネイティブ検索・キー処理の個別測定値、`*.stderr.txt` は
子プロセスの診断である。IMEの保存設定・学習履歴・実入力は収集しない。
本文を含む出力はgit対象外の `out/` に置き、リポジトリには本文を含まない集計だけを残す。

```powershell
# 完了済みの実行を再集計する。推論は再実行しない。
python -B scripts/evaluate.py --report out/evaluation-new
```

再集計は完了フラグと要求数を確認し、収集時のスクリプトのハッシュを保持したまま
`analysis_script_sha256` に集計コードのハッシュを残す。今回の記録も収集後に対象外の読み・
生成文字数等の集計を追加したため、この2つのハッシュは異なる。
異常応答・子プロセスの終了・応答待ち上限では中断し、未完了の記録を完了扱いしない。

## データと判定方法

- [AJIMEE-Bench](https://github.com/azooKey/AJIMEE-Bench/tree/401666cd56d1a570c2021798b64b6da4396bfd45) の
  `JWTD_v2/v1` 全200例。日本語Wikipedia入力誤りデータセットv2由来、CC-BY-SA 3.0。
  提供された左文脈がある100例・空の100例を、どちらも「文脈なし」「提供された左文脈」で評価する。
  表の「左文脈」は200例すべてに非空の文脈があるという意味ではない。
  入力のカタカナをひらがなへ変換し、公開されている許容解のいずれかとの完全一致を正解とする。
  読みを分割せず、正解文字列の表記を正規化しない。CERは計算していない。
- [自作32例](../tests/fixtures/quality-cases.json) は評価前に期待値を指定した診断データ。
  同音異義語24例、送りあり4例、句の生成4例を含み、文脈なし・左のみ・左右の3条件で測る。
  使用頻度に従う標本ではない。送りありは現在のIMEと同様に採点だけを行う。
- 負荷試験は、同じかな文を繰り返した32〜1024文字の生成と、末尾に数字を付けた2・20・64候補の
  採点。各5回。正解ラベルを持たず、品質の分母には混ぜない。

[skk-zenzの評価コード](https://github.com/nekomimist/skk-zenz/tree/db1c923223a94c6406fd19e4d75ef3b54bdf9300/scripts)
を参考に、上位候補の完全一致、長さ別集計、promote前後の比較を行う。
AJIMEEの判定定義は同リポジトリの `utils.py`（CC0）も参照した。外部の評価コードやデータ本文は同梱しない。

同じ例を3回測るが、正解率は最初の計測結果だけから求める。反復は遅延の標本数だけに加える。
失敗・対象外の読み・空の結果も分母に残す。top1、top5、候補内に正解が存在する割合、MRRを記録する。
各例を等しい重みとし、パーセンタイルは昇順のnearest-rank方式を使う。

文脈は前の末尾40文字・後の先頭40文字まで。生成5候補、採点は辞書先頭20候補。
採点の比較では最良スコアが元の先頭を1.0より大きく上回ったときだけ、その1候補を先頭へ移す。
採点しなかった末尾も含め、他候補の順序は保つ。

「モデル生成」はサーバーの生の候補順。「規則適用後」は期限とIMEの対象文字を確認し、
読みと同じかな表記・置換文字・重複・最良スコアとの差が8を超える生成候補を除いて、
10文字以上なら辞書の先頭へ、それ未満なら末尾へ追加した**到達可能な候補順**を表す。
短い読みの生成は実際には候補枯渇後なので、初回Spaceで見える候補順の実測ではない。
採点は単独で有効にした場合の比較であり、生成優先と同時に有効なIME全体の再現ではない。
候補操作・編集待ち・フォーカス変更による応答破棄もこのオフライン集計には含まない。

## 2026-10-06の品質結果

モデルはzenz-v3.2-small Q5_K_M、4スレッド。固定版・ライセンスは [依存一覧](../third_party/README.md)。
Windows 11 10.0.26300、AMD64 Family 25 Model 97、32論理プロセッサ、MSVC 19.44のRelease版で測定した。
辞書は175,779見出し・240,285候補、スキップした不正行2件、未対応候補0件。
評価の前後で辞書とモデルのハッシュが変わっていないことを照合した。

### 採点による順位と操作回数

診断の採点28例では、辞書のtop1が11/28、top5が27/28、全例で正解が候補内に存在した。

| 条件 | top1 | MRR | 改善 / 悪化 / 同順位 | Space＋Enter平均 | PageDown＋数字平均 |
|---|---:|---:|---:|---:|---:|
| 辞書順 | 11/28 | 0.624 | — | 2.250 | 1.000 |
| 左文脈で採点 | 27/28 | 0.982 | 16 / 0 / 12 | 1.036 | 1.000 |
| 左右文脈で採点 | 27/28 | 0.982 | 16 / 0 / 12 | 1.036 | 1.000 |
| 文脈なしで採点 | 10/28 | 0.597 | 1 / 4 / 23 | 2.357 | 1.000 |

操作回数は「第一候補が表示済み」から数える。0始まりの正解順位を `r` とし、Spaceで送ってEnterなら
`r + 1`、7件ページのPageDownと数字選択なら `floor(r / 7) + 1` 回とする。読みの入力、待ち時間、
登録手間、実際の利用者の操作は含まない。正解がない場合は架空の回数を割り当てず、候補内の有無を別に示す。
同じ28例同士では左文脈によりSpace＋Enterが平均1.214回減り、文脈なしでは0.107回増えた。
数字選択では正解が全て最初の7候補内にあり、回数の削減はない。

## 遅延の測定範囲

モデル要求はUTF-8 JSON Linesの標準入出力で逐次実行する。時間にはPython・JSON・パイプの往復も含む。
生成用・採点用に別サーバーを起動し、各1回のウォームアップを除く。並行する利用者の待ち時間は測っていない。
プロセス起動からhelloは生成37.599ms、採点38.514ms。OSファイルキャッシュは消去していない。
評価序盤には補助プログラムの別構成ビルドも行っており、無負荷に隔離した端末での計測ではない。

`nskkzime_eval_core` は実際の辞書と入力コアを使う。6キー列を各1,000回再生し、キー判定・試行コピー・
状態更新・未確定文字列生成・採用までをネイティブで測る。辞書検索は各例20回で、それぞれウォームアップを除く。

| ネイティブの処理 | 標本数 | p50 ms | p95 ms |
|---|---:|---:|---:|
| コアのキー処理 | 46,000 | 0.0002 | 0.0013 |
| うち変換を開始するキー | 5,000 | 0.0005 | 0.0021 |
| 辞書検索全体 | 4,640 | 0.0001 | 0.0014 |
| 辞書検索ヒット | 560 | 0.0013 | 0.0024 |
| 辞書検索ミス | 4,080 | 測定分解能付近 | 0.0001 |

辞書のファイル読み込み・解析は181.691msで、検索測定には含めない。
TSF編集ロック・Windowsのキー配送・UI描画・辞書キャッシュの初回起動はこの表の対象外。
**キー処理p95 5ms・辞書候補提示20msの目標を端から端まで達成した証拠にはしない。**

## 長い読み・多数候補の負荷試験

| 条件 | 要求数 | p95 ms | エラー数 | 生成文字数の範囲 |
|---|---:|---:|---:|---:|
| 読み32文字 | 5 | 242.668 | 0 | 26〜32 |
| 読み64文字 | 5 | 470.901 | 0 | 53〜59 |
| 読み128文字 | 5 | 997.880 | 5 | — |
| 読み256文字 | 5 | 956.492 | 0 | 55〜75 |
| 読み512文字 | 5 | 463.834 | 0 | 1 |
| 読み1024文字 | 5 | 0.842 | 5 | — |
| 2候補採点 | 5 | 17.563 | 0 | — |
| 20候補採点 | 5 | 71.397 | 0 | — |
| 64候補採点 | 5 | 222.777 | 0 | — |

エラーを返すまでの時間も含む。128文字は期限付近で失敗し、1024文字は早期に失敗した。
応答の一般的なエラー文字列だけでは、期限とモデル内部の制限を厳密には区別できない。
成功した512文字では1文字の候補しか返らず、256文字でも入力に比べて短い候補になった。
**プロトコル上の1024文字上限は、全文を正しく変換できる上限ではない。**
EOSで完了した候補を返す実装でも内容の欠落は起こり得るため、成功率だけで品質を判断しない。

残る評価は実アプリのTSF・UIを含む遅延、利用実態に近いSKK単語列と学習後の辞書、長文の内容保持、
並行要求・低速CPUでの待ち時間である。この基準データだけを使って閾値やモデルを最適化せず、
変更時には別の評価データでも確認する。
